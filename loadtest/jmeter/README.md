# JMeter 购票压测

打开 `purchase-cancel.jmx` 后即可运行。该文件名称为兼容原有文件保留，但其中只包含登录、查询乘车人和购票，不会发送取消订单请求。每个用户会从 `1001` 至 `1019` 共 19 个车次的 102 个合法站点区间中随机选择一组，并随机选择未来 1 至 14 天的乘车日期。席别按照每车商务座 10、一等座 220、二等座 540 的实际容量比例随机分配；请求不指定车厢号和座位号，由购票服务完成具体选座。默认参数为 5000 个 `loadtest` 测试用户、5 秒预热和 120 秒持续时间。所有用户完成登录和乘车人查询后，会在同步集合点等待，直到当前线程组的全部线程到达，再直接放行购票；集合点最多等待 30 秒，避免初始化失败造成永久阻塞。执行压测前，需要自行在测试环境准备 `loadtest0001` 到 `loadtest5000` 账号及对应乘车人，测试数据不随项目提交。

前置条件：新的网关 Jar 已替换并重启；无 JWT 的购票请求返回 401；Nacos 中票务、用户和订单实例数量分别为 4、2、2。

新的 Ticket 服务不会在购票请求中同步创建整列车的日期库存。执行压测前，先在 `12306_ticket` 数据库执行 `loadtest/sql/prewarm-ticket-service-date-inventory.sql`。脚本默认预生成车次 `1001` 至 `1019` 从今天到未来 14 天的库存，结束时每个日期的 `actual_inventory_rows` 应与 `expected_inventory_rows` 相等。如果修改 JMeter 的车次范围或 `departure_offset_max_days`，需要同步调整预热脚本中的车次和结束日期参数。

在 JMeter GUI 中，先把 `用户定义的变量` 的 `base_host` 改成实际网关 IP，然后点击开始。成功的登录和乘车人查询结果被标记为不发送给监听器，因此正常情况下 `汇总报告` 只显示 `购票` 一行；初始化失败的样本会保留在报告中，同时停止该用户线程。同步集合点仅作用于购票请求，所有已就绪用户会立即发送购票请求。购票响应必须同时满足 `code=0`、`success=true` 和 `data.orderSn` 非空才计为成功。实际 QPS 由压测机、网关和服务端处理能力共同决定。运行结束后重点看 `购票` 行的 Throughput、Average、90% Line、95% Line、99% Line 和 Error %，并核对购票样本数是否等于计划用户数。

首次运行建议先设置 `-Jusers=1` 验证业务响应，再依次改为 50、200、500、1000、2000，最后运行 5000 用户。同步定时器的 Group Size 为 `0`，JMeter 会自动使用当前线程组人数，无需随 `users` 手工修改。该场景是一次瞬时抢票，不使用限速器；5000 个真实测试用户能够分散用户级限流压力，但实际吞吐量仍受压测机、网关、票务服务、订单服务和数据库容量约束。

非 GUI 执行并生成 HTML 报告：

```powershell
jmeter -n -t purchase-cancel.jmx -Jbase_host=192.168.126.100 -Jbase_port=9000 -Jusers=5000 -Jramp_up_seconds=5 -Jduration_seconds=120 -l results.jtl -e -o html-report
```

如果冒烟测试没有产生预期数量的购票样本，可增加 `-Jrecord_setup_samples=true`，临时把成功的登录和乘车人查询也写入结果，定位线程在哪一步停止；正式压测不要设置该参数。

每个用户只会发起一次购票，所以这是一轮“抢票售罄”压测，而不是可无限持续的成功购票压测。购票成功会持续占用座位和令牌；再次执行前，应通过测试数据清理或订单超时关闭完成库存回收，并确认 Redis 余票、座位位图和令牌桶已恢复。性能结论以汇总报告中 `购票` 行为准。

单一车次可成功下单的请求数不可能超过该车次、席别和区间的实际余票。你此前查询的 `1001` 次二等座共有 220 个座位，因此 5000 用户全部买同一车次时，后续业务失败是正常的售罄结果；若要评估数千次成功购票，需要准备足量余票，或把请求均匀分配到多个车次和日期。
